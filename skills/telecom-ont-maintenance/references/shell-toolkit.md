# 补全Shell安装记录

两台样本的应用环境都已使用BusyBox 1.38.0，包含409个工具，并装好抓包、测速和其他排障命令。完整工具清单和用途在[README第五节](../../../README.md#五补全shell)，这里写怎么选择程序、放置运行库和核对结果。

## 一、先看环境

先读取主系统和应用环境的CPU架构、ELF类别、字节序、当前命令路径、运行库、空闲内存及可写空间。样本情况如下：

| 项目 | 中兴ZXHN G7615V2 | ZNXT ZN-XG120 |
|---|---|---|
| 架构 | AArch64，小端 | MIPS32r2，小端 |
| 应用环境运行库 | glibc | glibc |
| 原生opkg架构标记 | `zx279133` | `en7580v2` |
| 后补工具对应的OpenWrt包架构 | `aarch64_generic` | `mipsel_24kc` |

这些OpenWrt包依赖musl，与光猫原有glibc不是一套运行库；厂商opkg也不接受这些包的架构标记。本次用独立运行库来运行选定的程序，不直接把OpenWrt软件源接到光猫原有包管理器里。

样本可用内存约140到160MB，是当时的空闲量，不是整机内存规格。根据实际资源补按需运行的工具，不据此推导大型常驻服务也能运行。

## 二、BusyBox 1.38.0

本次使用官方BusyBox 1.38.0源码，加入OpenWrt的`210-add_netmsg_util`和`220-add_lock_util`补丁，分别编译对应架构的静态程序。厂商应用启动脚本会使用`lock`和`netmsg`，配置新BusyBox时一起保留。

1. 读取旧BusyBox版本、`--list`和实际命令链接，核对厂商启动脚本使用的工具。
2. 核对新程序的ELF架构和SHA256，再读取新程序的`--list`。409是本次配置的工具数量，不代表任意BusyBox构建都带相同工具。
3. 在对应的可写应用层配置程序和链接，确认`sh`、`ash`、`lock`、`netmsg`以及SSH仍能按现有入口调用。
4. 中兴主系统额外工具包的内存副本和持久副本一并核对，保留原有厂商命令入口。原厂只读系统中的旧BusyBox不是此次替换对象。

应用环境中新版本已经可用，中兴额外工具包也已更新；主系统内存命令入口的整机重启恢复仍未验证。

## 三、四个静态排障工具

`tcpdump 4.99.7`（含libpcap 1.11.0）、`iperf3 3.22`、`ethtool 7.2`和`strace 7.3`来自各自官方源码，分别构建两种架构的静态程序，校验后放到应用环境的`/usr/bin`。

交叉编译在独立编译机进行，不在光猫上编译。strace 7.3的构建用到了较新的Linux UAPI头文件；导出头文件不等于替换光猫运行中的内核。

`ethtool`部分查询是否可用取决于厂商驱动。本次`-i`、`-S`等查询存在返回`Not supported`的情况，不把程序能启动写成所有网口功能都已支持。

## 四、独立运行库工具

后补工具来自OpenWrt 24.10.4官方软件包：`mtr`、`iftop`、`bmon`、`socat`、`curl8`、`dig`、`ip-full`、`ss`、`htop`、`lsof`和`jq`。其中`ip-full`与`ss`同属iproute2；`arping`已经由BusyBox提供，没有重复安装。

1. 在编译机解析选定包及其依赖，按软件源索引和对应校验文件核对SHA256。
2. 将程序、匹配的musl加载器、依赖库、terminfo和CA证书解包到独立目录`/opt/owrt`，保留包内相对目录结构。
3. 在`/usr/bin`配置命令入口，使用对应的musl加载器和`--library-path /opt/owrt/lib:/opt/owrt/usr/lib`启动实际程序；不全局修改厂商程序使用的运行库路径。
4. 对照每个工具的实际文件位置配置入口，`mtr-packet`等辅助程序也要能通过对应的加载器启动；不能只让主程序显示一次版本号就算完成。
5. 保留厂商原有curl，新版命名为`curl8`。`lsof`使用独立包的完整版，不再指向BusyBox的同名入口。

独立目录在本次样本中约占15到18MB。暂存和解包前分别检查内存文件系统与应用存储空间，不能用闪存剩余量判断`/tmp`是否放得下。

### curl8的启动处理

本次一台样本启动curl8时卡在读取`/dev/random`。处理只放在curl8启动入口：建立独立挂载环境，再把`/dev/urandom`绑定到该环境的`/dev/random`。其他程序看到的设备节点不变，不把这个处理扩展为全局替换。

## 五、按实际网络条件检查

本次两台光猫只做桥接，自身没有配置外网路由和DNS。公共域名访问失败，不能直接当成工具安装失败；先用实际可达的局域网目标检查。

- `mtr -n <LAN_TARGET_IPV4>` - 使用数字地址查看路径，不等待域名反查。
- `lsof -n -P` - 使用数字地址和端口查看进程连接，避免解析等待。
- `curl8` - 先检查版本和可达的内网HTTP接口，再按实际CA证书配置检查HTTPS。
- `dig @<DNS_SERVER_IPV4> <TEST_NAME>` - 明确指定可达DNS服务器，不假设光猫已经有默认DNS。
- `ip-full`、`ss`、`htop`、`iftop`和`bmon` - 对照现有网卡、连接和进程核对输出。
- `jq` - 用不含凭据的样本JSON检查提取字段和整理结果。

这些是设备维护时的检查项目，不是编写文档时自动运行的测试。编写或更新本仓库只做静态校验。

## 六、轻量任务和固件资料分开写

自定义任务以定时检查网络、收集状态、转发日志、检查局域网接口等轻量操作为主，按需调用现有工具。

外部机型切换公版界面的案例作为拓展阅读。修改定制配置、刷地区固件和刷OpenWrt是不同的事情，本次两台没有验证可用的替代系统，不由当前root Shell或工具数量推导出可刷系统的结论。
