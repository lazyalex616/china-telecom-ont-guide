# 上海、浙江电信光猫：开启 Telnet 和 SSH 补全Shell

先看 [README](../../README.md)，按用户的目标进后台、开 Telnet 和 SSH、补全Shell。跟用户说话用自然的短句，直接说做到了哪一步、接下来做什么。

先拿到光猫超密，再开始。

按用户这次要做的项目选章节：进后台、配置SSH、补全Shell、对时和日志收集分别处理。只查现状时，读配置、进程和已有记录即可。

## 这次用的设备

| 样本 | 固件 | 架构 | 已完成 |
|---|---|---|---|
| 上海电信，中兴 ZXHN G7615V2 | `V3.0.0P1T2` | AArch64 / ARM64，小端 | 主系统Telnet、SAF应用SSH、BusyBox 1.38.0与排障工具、常驻对时和日志转发 |
| 浙江电信·嘉兴，ZNXT ZN-XG120 | `ZV2.01.X01` | MIPS32r2，小端 | 主系统Telnet、SAF应用SSH、BusyBox 1.38.0与排障工具、常驻对时和日志转发 |

两台都配了自启动，还没重启试过。中兴主系统里新加的命令入口，重启后能不能恢复也还没试。

## 一、先连上光猫

先看光猫地址是多少、谁在拨号、路由器哪个口接光猫。`192.168.1.1` 是这里用的示例地址。

- 直接连光猫 Wi-Fi 或网口：打开光猫地址。
- 光猫拨号、后面接路由器：看后面路由器的连接方式、地址和访问设置。
- 路由器拨号、光猫桥接：看静态路由、接光猫一侧的地址，以及光猫怎么把回复送回来。

把需要的设置补上，再试一下能不能进后台。

用爱快的话，先看 [ikuai-cli](https://github.com/ikuaidev/ikuai-cli)，让Agent在电脑上装好 CLI 和 Skill。选好要连的路由器，读取现有接口和规则，把去光猫后台的路配好。

## 二、登录后台

照网页实际使用的请求流程提交账号和密码，处理跳转，保存登录状态。

### 中兴 ZXHN G7615V2

- 8080 端口 `/login.cgi`，表单字段为 `username`、`psd`。
- 登录后跳到 `/start.ghtml`，保存 SID。
- 从 `/template.gch` 看页面引用，再读对应的 `/getpage.gch` 子页面。

### ZNXT ZN-XG120

- 先经过 80 端口页面，再向 8080 端口的 `/login.cgi` 提交登录请求。
- 表单字段为 `username`、`psd`，返回结果包含 `auth_result`。
- 按网页 JavaScript 的做法，把 `ecntToken` 写进同名 Cookie。
- 读取 `/cgi-bin/content.asp` 和它引用的子页面。

进去后看一下型号、固件和拨号方式。卡住就查请求地址、字段、跳转、登录状态、来源、编码和权限。

## 三、开启 Telnet

按[主系统Shell和原生配置](references/native-shell-config.md)处理当前型号的登录、主系统与应用环境，以及配置保存和生效。

中兴这台用`webFac v3`临时维护登录：识别`re_rand`响应，按光猫实际看到的管理连接来源构造请求，用超密完成认证，再读取返回的临时Telnet账号。协议资料在[参考项目](../../THIRD_PARTY_NOTICES.md)里。

ZNXT这台在后台开Telnet，再用对应的命令行账号登录，需要时用管理员账号执行`su`。这台Telnet使用LF换行，中兴使用CRLF。

进去后用`id`核对UID 0，再看CPU架构、位数、字节序、剩余空间、PID 1和当前进程环境，分清主系统root与应用root。

需要改配置时，网页路径按实际RSA+AES参数封装和会话流程提交；本机路径使用固件自带的命令。只有确认目标固件的调用约定后，才用参考文档中的native-ABI helper处理对应的原生日志发送。保存值、运行状态和NAS实际接收分别核对，helper不替代配置保存。

## 四、装好 SSH

这次用的是从 [Dropbear 上游](https://github.com/mkj/dropbear) 编译的 2026.94 静态程序。给当前 CPU 准备对应的程序，传过去后核对文件。

光猫自带的 SAF 应用环境里有 `procd` 和 `rc.common`。先从主系统Shell找到当前应用管理进程、根目录和可写层，再进这个正在运行的环境安装。

实际的`appmgr`定位、`nsenter`命令模板、Dropbear启动参数和收尾步骤见[详细步骤](references/native-shell-config.md#五装好ssh再核对连接环境)。

1. 看一下现有服务，单独找个目录放程序。
2. 放好登录用的公钥，给光猫生成自己的主机密钥。
3. 配好监听地址、文件权限和启动参数。
4. 用应用环境自带的启动方式配好服务和自启动。
5. 在电脑上核对主机身份，连一次 SSH，试一下命令。
6. 记下连接方式和安装位置，把这次临时开的 Telnet 关掉。

## 五、补全Shell

两台样本的应用环境都已使用BusyBox 1.38.0，带409个工具；中兴主系统里额外补充的工具包也更新为这个版本。原厂只读镜像中的旧版本仍保留，不把它们误记成当前新增工具的版本。来源见[参考项目](../../THIRD_PARTY_NOTICES.md)。

### 补全的Shell有哪些：

1. BusyBox 1.38.0 - 提供ash、文件操作、文字处理、网络检查和对时等409个工具。
2. tcpdump - 抓取数据包，核对实际收发情况。
3. mtr - 持续查看沿途每一跳的延迟和丢包。
4. iperf3 - 检查网络吞吐和UDP丢包。
5. curl8 - 测试HTTP、HTTPS接口，保留厂商原有curl。

完整清单放在[README的默认折叠块](../../README.md#五补全shell)，包括四个静态排障工具和后补的11个命令入口；`ip-full`与`ss`同属iproute2，`arping`已经包含在BusyBox里。

### 补全Shell可以：

1. 查文件、筛日志、改文件、查网络、跑脚本、处理日志……
2. 按需跑轻量自定义任务，检查网络、收集状态、转发日志和检查接口结果。
3. 查找对应机型的固件和界面资料，区分外部案例与这两台样本的实际完成项目。

按[补全Shell安装记录](references/shell-toolkit.md)核对架构、现有命令和运行库，再选静态程序或独立运行库方式。样本后补工具来自OpenWrt 24.10.4官方包，但厂商opkg不能直接安装这些包；运行库放在`/opt/owrt`，命令入口单独配置，厂商curl保留，新版使用`curl8`。

只补实际需要且能运行的命令行工具。通用OpenWrt软件目录不是这两台光猫的安装清单，内存、存储、厂商运行环境和驱动条件都按现场核对。本次不把大型常驻服务列作已实现功能。

## 六、光猫对时

当前两台样本都采用`上游NTP → wrt的chrony → 本地管理转发 → 光猫ntpd`，持续对时，不再使用定时Telnet校时脚本。

1. **wrt提供时间。** 两边均运行chrony 4.6.1，替换原来的BusyBox sysntpd；旧客户端已停止并取消自启，避免两套程序同时调整wrt时钟。
2. **六个上游参与选源。** 配置为`ntp1.aliyun.com`、`ntp.tencent.com`、`time.asia.apple.com`、`time.cloudflare.com`、`ntp.nict.jp`、`time.edu.cn`，使用`iburst`和`maxpoll 10`。chrony按状态调整轮询，`maxpoll 10`对应1024秒，不是固定每小时校一次；六个地址也不直接等于六套完全独立的基准时钟。
3. **光猫持续同步。** SAF应用环境里的BusyBox 1.38.0运行`ntpd -n -p <ONT_VISIBLE_TIME_SERVER_IPV4>`，由procd服务`ontntp`管理，启动项为`S95ontntp`。样本应用环境具备`CAP_SYS_TIME`且与主系统共享时钟，所以能校准整机时间。
4. **管理地址按现场转发。** 光猫可访问的时间服务器地址，通过现有管理路由及对应UDP 123转发到本站wrt。爱快在这条路径里做转发，不再是光猫实际跟随的时间源；原有爱快NTP服务是另一项配置。
5. **检查进程、选源和时钟状态。** 在wrt读`chronyc -n sources`和`chronyc tracking`，在光猫读服务状态与`busybox adjtimex`；测时间偏差时单独记录采样方法，HTTP返回的整秒时间不能证明毫秒级精度。

旧的Telnet校时程序、定时任务和运行配置已删除，不把旧方案与当前方案同时配置。两边均已核对当前服务和启动项，整机重启恢复还没验证。

## 七、把光猫日志收到NAS

先看现有日志来源、发送程序、路由和NAS接收端，再选择对应做法。两台样本都是光猫主动发送，不是由wrt定时登录复制日志。

1. **中兴使用固件自带的日志发送功能。** 对应配置是`Log`表的`ServiceIp`、`ServicePort`、`ServiceEnable`，分别填写接收地址、端口和开关。保存配置和启用当前发送程序是两件事，分别读回，再到NAS看真实设备日志有没有新增。
2. **ZNXT使用应用环境里的日志读取程序。** 从已有共享路径`/e8cvar/log/messages`持续读取主系统新增日志，通过Lua/nixio发送，用SAF自带的procd和启动项运行。原有syslogd保留本地记录，应用读取程序负责网络发送，避免与旧的`-R`转发重复。
3. **通过现有路由送到NAS。** 样本用不同UDP端口区分设备，NAS的rsyslog分别接收，各自写入`<日志目录>/<设备名>/ont.log`。接收地址、端口和路径按现场填写，公开材料使用用途占位符。
4. **在NAS上保存和查询。** 光猫日志单独按天轮转，样本最长保留366天，其他设备原有保留规则不变。ZNXT读取程序的进度放在内存，转发程序不额外将日志写入光猫闪存；这不代表固件原有的日志写入也被关闭。
5. **核对原始内容和时间。** 对照主系统已有日志与NAS记录，区分原始事件时间和转发时间。UDP没有送达确认，网络或NAS故障期间可能丢记录；一年保留期限不代表一年日志必然完整。

两台样本都验证过真实日志到达NAS。中兴已保存原生配置，ZNXT已配置应用自启动，两台都还没重启验证恢复情况。
