# 10：两个案例最后变成什么样，以及为什么这次走了弯路

## 一、这不是全国统一配置表

这只是两台已授权设备的整理结果：

- 上海电信，中兴 ZXHN G7615V2；
- 浙江电信，ZNXT ZN-XG120。

固件、业务和端口绑定不同，就不能直接照抄。

## 三、哪些东西没有被为了“对齐”而复制

- 没把上海 VLAN 改成浙江的；
- 没把浙江 VLAN 改成上海的；
- 没复制 MAC、LOID、SN 或局端身份；
- 没把没有无线硬件的设备当成带无线模块；
- 没把两家厂商的数字枚举当成同一标准；
- 没为了校时恢复运营商管理通道；
- 没降低 iKuai 的整套安全防护。

所谓对齐，应该是对齐你想要的**功能结果**，不是把两台机器每个字段都变成一样。

## 四、最重要的错误判断：把不同层面的“断网”混到一起

最初看到的有：

- 拨号保活不回应；
- `PADO` 超时；
- 光猫相关网口多次 down/up；
- 运营商提供的上网会话时间。

这些线索曾被过早组合成“问题在光纤上游”。

后来确认：

- 一部分拨号失败发生在光猫自己处于路由拨号、下游 iKuai 还在 PPPoE 的阶段；
- 运营商截图首先是账号上网会话，不是直接的光口掉线证明；
- 物理网口抖动不能当作已经排除网线；
- 最终现场重新插牢光猫到小主机的网线后，频繁断网恢复。

这说明：**应该随新证据撤回旧结论，不能为了维护先前说法继续找理由。**

## 五、为什么登录和修改花了不必要的时间

### 1. 没一次复现完整认证

一开始把一个浏览器过程拆成几个看起来相似的请求，却漏了真正建立会话的步骤、字段和 JavaScript 写入的 Cookie。

结果是反复重试，还把流程问题说成了密码问题。

更好的做法：先读完整成功流程，再验证一条内容页，而不是先试一串接口。

### 2. 没先确认故障层级

对时没有成功时，先猜是防火墙拦截，却没有先证明光猫发出了请求。

还把一个名字像“监听接口”的字段误当成 NTP 绑定字段。它实际属于另一个功能，后来恢复了原值。

更好的做法：先区分“没启动、没发出、被拦截、没回应、回应无效”，再决定改哪里。

### 3. 把源码默认变量当成真实状态

浙江防火墙页面里有个值为 `1` 的变量，曾据此解释为低档。独立读取实际 `selected` 后才确认选的是高档。

更好的做法：追服务端值、加载函数、当前控件和保存后的回读，不照搬别家的数字含义。

### 4. 没先核对工具与固件

最小 OpenWrt 的命令参数、Python 模块和编码支持，与桌面 Linux 不一样；新固件认证协议也不一定被旧工具支持。

错误调用后再一点点猜，会形成很多没有新证据的重试。

更好的做法：只检查当前操作需要的实际能力和当前设备返回的协议特征，遇到未知版本就明确停止。

### 5. 会话和工作没有连续管理好

过早清理仍可复用的登录状态、反复重新抓取相同页面，会增加返工。

已经得到明确授权后，多次停下来交半成品、重复问同一件事，也会把一个连续任务拆成很多轮。

更好的做法：保留安全会话，按明确范围连续做完；只有真正扩大范围或出现新的影响时才暂停。

## 六、真正需要花时间的部分是什么

两台不同固件，确实存在真实差异：

- Web 认证和会话不同；
- 中兴表单有加密封装；
- 临时命令访问协议不同；
- Telnet 换行和 shell 提示符不同；
- 原生 NTP 在当前桥接配置下没有工作；
- 本地服务启用后还要验证公网访问限制；
- 最后要核对实际时钟、调度和业务没有被破坏。

这些需要认真处理，但不能拿它们为前面的盲试、误判和重复确认开脱。

## 七、以后应该怎么做

固定成这条路径：

```text
确认所有权和授权
    -> 确认当前设备与真实状态
    -> 复现一次完整成功请求
    -> 用进程/包/日志定位问题层级
    -> 构造最小改动
    -> 独立回读
    -> 验证业务与安全边界
    -> 记录可复用方法
```

不要用“我已经下载了很多页面”代替读懂配置，也不要用“返回成功”代替验收。

## 八、本仓库验证到哪一步

### 实际案例已经验证的

- 两个样本的成功登录路径；
- 对应页面里的配置读取；
- 经机主授权的目标设置修改及回读；
- 原型方案对光猫实际系统时间的校准；
- 多次真实定时执行；
- 本地时间服务与外部访问限制；
- 修改后的拨号和基础外网连通。
- 后续两台原生 SAF 应用内 SSH 的主机身份核对、密钥登录、命令执行、权限、监听和启动项回读，以及本次临时入口清理。

### 不应该声称已经验证的

- 所有省份、型号和固件；
- 每个隐藏功能和所有动态配置组合；
- 所有转发路径的性能和硬件卸载；
- 恢复出厂后的行为；
- 未经授权就重启设备模拟故障的结果；
- 本仓库公开整理版在每个读者环境的运行效果。
- SSH 的整机或应用重启恢复、公开启动模板新增校验的设备运行结果。
- 由应用 SSH 自动取得主系统日志、恢复主系统命令或完成日志重启恢复。

公开整理版检查的是文件、语法、示例、链接、Skill 结构和脱敏，不是又拿生产设备做一轮新部署测试。

SSH 的完整过程和两个系统视图的区别见 [第 12 章](12-native-app-ssh.md)。公开版本保留了方法，没有复制实际站点入口、密钥、指纹或私有连接注册表。

## 九、给读者最后一句建议

拿到超密以后，不是权限越大越该多改，而是越要知道自己在改哪一层。

**读清楚、只改目标、保留证据，比“所有选项都统一”重要得多。**
