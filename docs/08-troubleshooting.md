# 08：常见失败现象，先查哪里，什么时候停

[返回首页](../README.md)

## 一、访问和登录

| 现象 | 先查什么 | 不要马上做什么 |
|---|---|---|
| 能 ping，网页登录超时 | 路由、管理接口地址、端口、回程、是否访问了正确设备 | 不要把超密直接发给未确认身份的地址 |
| 80 端口能开，8080 不行 | 当前设备真正提供哪些入口、网络策略 | 不改全局代理，不盲目开放公网管理 |
| 浏览器能登录，脚本说密码错 | 两段认证、字段、Cookie、JS 写入的 token、frame | 不重置密码、不猜默认口令 |
| HTTP 200 | 返回的是模块、登录页还是错误页 | 不凭状态码宣布成功 |
| `Privilege=0` | 同时看 `Logged`、`Locked`、页面错误分支 | 不统一翻译成密码错 |
| `Logged=1` | 是否已经有一个有效会话占用 | 不靠重启或恢复出厂“踢人” |
| 内容页 302 | 会话和框架是否完整，是否过期 | 不直接说没有这个功能 |
| 子页总跳回主框架 | 当前 frame 和来源上下文 | 不盲扫更多子页 |
| 登录几次后要等一分钟 | 是否真的触发锁定，之前调用是否完整 | 不做自动无限重试 |

### 页面上“锁定键已开启”不一定是账号被锁

它可能只是大写锁定键提示。

账号锁定状态应根据后台明确状态和页面分支判断，不要只看到“锁定”两个字就下结论。

### 请求在本机就没启动，不是光猫拒绝登录

例如操作系统拒绝启动脚本、权限不足、程序路径错误，发生在 HTTP 请求发出去之前。

应该报告执行环境错误，而不是说“光猫密码又失效了”。

不要靠关闭杀毒、降低系统安全设置或把密码写进临时脚本来绕过问题。

## 二、页面看起来读到了，但值很奇怪

### 源码变量、表单值和最终显示不同

按顺序追：

1. 服务端填入的值；
2. 隐藏表单字段；
3. 加载函数的修改；
4. 下拉框实际 `selected` 和勾选框实际 `checked`；
5. 保存后独立重读。

不要把 `N/A` 自动当成 0，也不要把 `-` 自动当成正常值。

### 抓到的是通用页面模板

没有无线硬件的设备，也可能提供无线设置页面的模板。

应同时看设备能力、菜单是否展示、真实状态和页面是否可操作。报告“模板存在”就好，不要凭模板说硬件一定存在。

### 页面数量变多或变少

固件、用户权限、菜单条件、当前对象、跳转和会话都会影响数量。

数量不是验收指标。覆盖清单和实际读取到的对象才是。

## 三、保存失败或保存后没变化

| 现象 | 可能漏了什么 |
|---|---|
| 返回成功，但重读还是旧值 | 实际提交对象、字段、当前模板、保存分支或动态值 |
| 表单被拒 | 会话票据、`EBOOVALUE`、字段顺序/编码或当前页 token |
| 中兴明文字段不被接受 | 页面可能将参数加密到 `IF_ENCODEPARAM` 并封装 `IF_ENCODE` |
| 默认选择的是另一条 WAN | 你还没切到目标对象，就构造了请求 |
| 某备注被 API 拒绝 | 字符限制，不一定是 Token、接口或网络坏了 |

**失败后先保留现场和会话，不要立即清空所有临时状态再从头试。**

确需保留的会话文件放私密目录，不能带进 Git。包含凭据的无用副本及时安全清理，但不要把正在使用的登录状态当垃圾删掉。

## 四、NTP 能取时，光猫还是 1970 年

按这个顺序分开：

1. 本地时间源本身是否准确；
2. 测试请求是谁发出的；
3. 光猫的原生客户端是否启动；
4. 请求是否从正确接口发出；
5. 请求有无回应；
6. 返回包是否有效；
7. 设置的时间是不是光猫真实系统时间。

不要先把防火墙全部关掉。

如果原生客户端就是只认路由 WAN，而当前只剩桥接，继续在同一个无效页面上反复保存地址和等待，通常不会带来新证据。

## 五、命令访问失败

### Web 超密不能替代所有其他密码

Web 管理、本地 Telnet、`su` 可能各用一套凭据。

只使用已合法取得或经明确授权从本机读取的值，不提供默认密码表，不做字典尝试。

### 登录名和密码都对，仍然报错

检查终端协议细节：

- 设备要 LF 还是 CRLF；
- 是否多发了一次空行；
- Telnet 协商是否正确；
- 密码是否已经发送到真正的密码提示后；
- 是否需要先登录再 `su`；
- shell 提示符是不是带路径前缀，例如 `/#`。

这些不对时，也可能出现看起来像“账号密码错误”的结果。

### 中兴握手返回 `re_rand=`

这表示不能继续套只支持空响应或 `newrand=` 的旧流程。

先辨认当前协议，使用相应实现。未知协议应停止，不能用固化、刷机或改 MAC 的办法硬凑。

## 六、OpenWrt 的最小系统和普通 Linux 不一样

### 命令名字在，不代表参数一样

样本环境曾遇到：

- 没有 `timeout`；
- 没有 `comm`、`paste`；
- BusyBox `nc` 不接受某些常见参数；
- 某个命令最后的 `grep` 没匹配到内容，返回 1。

不能把这些本机命令错误写成“远端端口关闭”“SSH 断了”或“设备坏了”。

### Python 也可能不是完整标准库安装

可能缺少：

- `urllib`；
- `email`；
- `ssl` 或 `_ssl`；
- `idna` 编码；
- `gb18030` 编码。

所以，即使有 `python3`，也不能假设桌面系统上能跑的脚本原封不动都能跑。

公开校时工具使用 curl 和 OpenSSL 处理相应通信，避免依赖一大套 Python 网络库；但仍应先核对它列出的实际依赖。

### 中文乱码

网页声明 `gb2312` 时，不要因为终端是 UTF-8，就把网页也当 UTF-8 解。

如果只是提取英文协议字段，可以保留原始字节再有针对性地解析；要读中文菜单，就按实际编码解码。不要看到一堆乱码后凭经验猜它写了什么。

## 七、临时入口没有关掉

先停止后续自动任务，明确报告清理失败。

已知差别：

- 浙江样本有独立的 Web Telnet 开关；
- 中兴临时服务可能叫 `utelnetd` 而不是 `telnetd`；
- 系统时间大幅跳变后，原来的 Web 会话可能失效，需要正确重新认证一次才能关开关；
- 普通 TCP 握手成功未必代表真实 Telnet 服务还在；
- 原本就存在的用户会话不能冒充成自己开的临时入口去关闭。

不要因为时间已经正确，就忽略剩下的管理入口。

## 八、原生应用 SSH 的几种误判

| 现象 | 应该区分什么 |
|---|---|
| 端口返回 Dropbear，但 `ssh-keyscan` 报 `unsupported KEX method` | 可能是特定客户端算法兼容问题，不能仅凭它判定转发不通；从可信控制台核对主机身份，不关闭严格校验 |
| 登录后 `id` 是 root，但看不到主系统进程 | 可能在 SAF 应用环境，核对 PID 1 和根目录，不能假定已经进入主系统 |
| `stat: not found` | 应用 BusyBox 的命令集可能更旧，不是 SSH 断开；改用已确认存在的权限读取工具 |
| 启动链接有了 | 只能证明启动项登记，不能报告已经实测重启恢复 |
| 两个站点都是同一个管理地址 | 先明确站点入口、目标身份与回程，不把同地址当同设备 |

方法、公开模板和样本验证边界见 [第 12 章](12-native-app-ssh.md)。没有当前固件证据或具体操作授权时，不运行安装。

## 九、什么时候不要再试

- 已经分不清访问的是哪台设备；
- 没有有效凭据；
- 错误分支和目标对象还没看懂；
- 没有明确授权；
- 下一步会改拨号、光路身份、固件或唯一管理路径；
- 无法解释提交内容；
- 无法验证或关闭临时入口。

有边界地停止，比为了交一个“成功”结论继续扩大操作更可靠。
