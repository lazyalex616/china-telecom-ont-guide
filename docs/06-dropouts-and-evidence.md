# 06：频繁断网，到底是光纤、光猫，还是下游网线

[返回首页](../README.md)

## 先把这次最重要的教训写在前面

浙江案例反复断网，换了光猫仍然有问题。最终现场确认：

> **是光猫到 ESXi 小主机之间的普通以太网网线没有插紧，重新插拔后恢复。**

此前曾根据拨号超时、网口 Up 和运营商“掉线”说法，过早倾向光纤侧。这种判断不够严谨。

这章不是要你每次都先怪网线，而是教你**别把某一层的现象，直接当成另一层的结论**。

## 一、先分清三段

```text
第一段：运营商 ── 光纤 ── 光猫
第二段：光猫 ── 普通网线 ── ESXi / 路由器物理网口
第三段：物理网口 ── 直通或虚拟交换 ── iKuai 拨号和内网
```

- 第一段可能有光功率、LOS、PON/ONU 注册等证据。
- 第二段可能有网口 Link、速率、错误包、重新协商等证据。
- 第三段可能有虚拟机、直通网卡、驱动、PPPoE 和路由配置等证据。

“整个站点从远程消失”只说明你的远程通道也断了，还没有指出哪一段坏了。

## 二、几类日志分别能证明什么

| 看到的现象 | 能说明什么 | 不能直接说明什么 |
|---|---|---|
| `ethX link down/up` | 这个接口的物理连接状态发生变化 | 单凭它不能区分网线、接口、光猫重启或人为插拔 |
| `PADO` 等待超时 | PPPoE 发现阶段没收到接入端回应 | 不能直接锁定光纤，也不能排除本地二层链路 |
| `No response to echo-requests` | 已建立的拨号会话保活没得到回应 | 不能凭这一行区分丢包、光猫、网线或局端 |
| 宽带“上网详单”有多次会话 | 宽带账号的上网会话中断、重建 | 不等于光猫的光路注册也掉了 |
| PON/ONU 离线或 LOS 告警 | 是光路侧的重要线索 | 仍需结合时间、供电、设备状态判断具体原因 |
| 网口现在是千兆全双工 | 当前协商状态看起来正常 | 不能证明十分钟前没抖动、接触一直良好 |
| 丢包计数是 0 | 对应统计口径当前没累计到丢弃 | 不等于 CRC/FCS 错误是 0 |
| ESXi 的 `vmnic0` 没掉 | 这个 ESXi 管理网卡没有相应记录 | 不能排除直通给 iKuai 的另一块网卡 |

### `PADO` 是什么，大白话版

拨号开始时，路由器先喊：“有没有接入服务器？”

`PADO` 是对方回应的一步。收不到回应，可能是喊声没发出去、路上掉了、光猫没转发，或者对方没回答。

它不是“电信光纤坏了”的专用错误码。

## 三、怎么和装维师傅对齐“掉线”的含义

可以这样问：

> 您看到的是宽带账号的 PPPoE 上网会话记录，还是这台 ONU 在 PON 侧的注册上下线记录？能否按同一个时间点对照一下，是否有 LOS/LOF 告警、掉电记录或光功率异常？

这不是和师傅争吵，而是确保双方说的是同一层。

如果对方发的是“上网开始时间、上网结束时间、流量”，它通常首先证明的是**宽带账号会话**，不能自动升级成“光纤断了”的证据。

## 四、为什么“路由模式稳定，桥接就掉”还需要做公平对比

案例里有一段时间，光猫改成路由模式，但后面的 iKuai 仍保持 PPPoE 拨号。

结果是：

- 光猫自己有一个拨号会话；
- iKuai 没有按新的网络结构正确拿地址；
- 内网实际上没正常上网；
- 光猫那条连接几乎是空闲的。

因此，“空闲挂着不掉”和“正常承载流量时掉”，不能直接证明桥接模式是原因。

但反过来，也不能说“有流量才掉，所以肯定是光纤”。

公平的对比要尽量保持：

1. 同一条线路和供电；
2. 相近持续时间；
3. 相近业务负载；
4. 明确知道是谁拨号；
5. 明确知道下游是 DHCP、静态地址还是 PPPoE；
6. 同时记录光路、网口、拨号三个层面的状态。

**切模式会改变网络结构，不要让 Agent 擅自改唯一的远程出口来“做实验”。**

## 五、换了光猫为什么仍不能排除网线

两台光猫可能共用：

- 同一根网线；
- 同一个水晶头；
- 同一个小主机网口；
- 同一根电源延长线；
- 同一段光纤；
- 同样的位置和散热条件。

所以“换了设备还一样”，只能缩小某些可能性，不能把共用的环节全排除。

本案例就是网线没有完全插牢，换光猫并没有解决这个共同环节。

## 六、发生故障时，最有价值的几项证据

尽量在同一时间窗口记录：

| 项目 | 为什么要它 |
|---|---|
| iKuai 系统运行时长 | 区分设备重启和线路中断 |
| 光猫真实运行时长 | 区分光猫重启与不重启的断链 |
| 光口注册/告警 | 看光路侧是否同时异常 |
| 接光猫的物理口状态和计数 | 看下游以太网是否抖动 |
| PPPoE 日志 | 看拨号在哪一阶段失败 |
| 光猫管理地址是否可达 | 观察本地管理路径是否也受影响 |
| 一个外网 IP 是否可达 | 尽量把 DNS 问题先分开 |
| DNS 查询是否正常 | 识别“能联网但域名打不开” |
| 时区和日志时钟是否准确 | 防止拿两个不同时间的事件硬凑因果 |

### ping 通光猫，也不是“上游光纤故障”的铁证

ping 只走了很小的一条管理流量路径。

它能证明这一刻有一条 ICMP 管理路径可用，但不能完全证明桥接业务的转发、VLAN、网卡收发和 PPPoE 数据路径都稳定。

所以不要写出：

> 能 ping 光猫，因此网线完全排除，肯定是光纤。

应该写：

> 同一时刻管理 ping 仍可达，说明管理路径未完全中断；桥接业务为何中断仍需结合其他记录。

## 七、光功率怎么看，别只记一个万能范围

首先确认：

- GPON、XG-PON 还是其他制式；
- 设备和运营商采用的光模块等级；
- 页面原值是什么单位；
- 是否需要换算；
- 有没有历史波动和告警。

不同页面可能返回：

- 已换算好的 dBm；
- 放大过的整数；
- 原始光功率数值，需要按页面公式换算；
- 无效占位符 `-`。

不能把另一家设备的“除以一万”公式直接套到当前光猫。

**某一次读到正常光功率，不能排除稍早的瞬态问题。** 正常阈值也应以对应设备和运营商规范为准，不要给所有型号套一个绝对数字。

## 八、远程一断就连不上，怎样取证

正确思路是本地记录、恢复后再读，而不是远程已经断了还反复发命令。

如果要新增本地诊断任务，先授权它的范围：

- 只读取哪些地址和接口；
- 采样频率；
- 日志大小上限和保留时间；
- 不含任何重拨、重启或修复动作；
- 记录什么字段；
- 怎样停止并移除；
- 不记录密码、完整账号和登录票据。

不要一上来放一个无限写日志、自动重启光猫的“守护脚本”。

## 九、报告应该怎么写

推荐四段：

1. **事实**：什么时间、哪一层、观察到了什么。
2. **不能证明什么**：主动说明证据边界。
3. **目前假设**：哪些可能性还在，依据是什么。
4. **下一项验证**：做什么能区分这些可能性。

例子：

> 接光猫的以太网口出现多次 down/up，拨号随后中断。该记录支持检查光猫网口、网线和小主机网口，但不能单独证明哪一头损坏。需要把同一时间的光路注册记录和接口计数对照。当前不改桥接、不改拨号、不重启。

不要为了让报告显得“有结论”，提前把推测写成已经排除或已经定位。
