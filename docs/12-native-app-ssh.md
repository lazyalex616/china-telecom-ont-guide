# 12：两台光猫怎样连上 SSH，以及为什么登录后还不是主系统

[返回首页](../README.md)

**这不是发现了一个通用 SSH 开关。我们先使用合法的临时维护通道，再在光猫已有的 SAF 应用环境内安装 Dropbear，最后通过后级路由器提供独立的内网入口。没有刷固件。**

前提仍是本人或已明确授权设备，并已从装维师傅取得当前有效超密。开启临时命令入口、安装服务、增加自启动、修改路由器和真实登录验证，都要有对应授权。阅读、下载或安装 Skill 不代表获得这些授权。

## 一、先看结果和验证边界

| 样本 | 本次使用的硬件架构 | 实际结果 | 尚未验证 |
|---|---|---|---|
| 上海电信，中兴 ZXHN G7615V2，`V3.0.0P1T2` | AArch64 / ARM64，小端 | 原生应用内 Dropbear 2026.94，密钥登录和命令执行成功，启动项已注册 | 光猫重启或应用环境重启后的恢复 |
| 浙江电信，ZNXT ZN-XG120，`ZV2.01.X01` | MIPS 小端 | 原生应用内 Dropbear 2026.94，密钥登录和命令执行成功，启动项已注册 | 光猫重启或应用环境重启后的恢复 |

这些是两个已授权样本的历史结果，不是本次发布重新测试。**公开启动模板增加了占位地址和地址校验，只完成静态检查，没有重新部署到生产设备。** 相同型号、不同固件也需要重查。

## 二、完整路径是什么

```text
安装阶段：
已有合法 Web / 临时 Telnet 维护通道
    -> 主系统 root
    -> 进入已存在的 SAF 应用环境
    -> 安装对应架构的 Dropbear、公钥和原生启动项
    -> 核对身份、实际 SSH 登录
    -> 关闭自己临时开启的 Telnet 和传输入口

后续连接：
管理电脑 -> 内网或已授权的私有隧道 -> 站点路由器独立端口
    -> 光猫管理 IPv4:22 -> SAF 应用环境的 root shell
```

Telnet 只是初次安装通道，不需要为了以后用 SSH 而永久开启。原有校时任务是否仍临时使用 Telnet，是另一件事，不能擅自停掉。

## 三、怎样取得安装权限

- **中兴样本**：用已取得的有效超密走匹配固件的 `webFac v3` 临时维护认证，取得本次会话的临时登录信息。
- **ZNXT 样本**：通过合法 Web 会话临时打开 Telnet，再用已合法取得的命令行凭据登录和提权。
- Web 超密、Telnet 密码和 `su` 密码可能不是同一个值；没有就停止，不猜、不用默认密码表。
- 临时 Telnet 不是加密通道，只能在已核实可信的管理链路中使用。

本仓库的 [校时工具](../tools/ont-clock.py) 仍然只做它声明的校时任务，**没有新增“打开一个长期 shell”模式**。不要拿 `--force` 当通用安装入口，也不要把私有运维脚本直接套到其他固件。

## 四、主系统 root 和应用 root 为什么不一样

SAF 应用环境可以理解为光猫内部另一个文件和进程视图。样本中它有自己的 `/sbin/procd`、`/etc/rc.common` 和可写应用层。

两个环境共享网络等部分资源，但看到的进程和根目录不同。因此：

- SSH 中 `id` 显示 `root`，**不等于已进入主系统**。
- 应用环境里的 `/etc/init.d/ontssh` 不等于主系统固件的启动脚本。
- 共享目录存在，不等于应用能看到全部主系统日志。
- 这也不是对隔离安全性的审计结论，不能认为应用 root 对整台光猫没有影响。

安装时在**已经授权取得的主系统 shell** 中，核对应用管理进程和它的根目录，再进入现有环境。下面只是命令形状，两个占位符必须从当前设备确认，不能复制旧 PID：

```sh
APP_PID='REPLACE_WITH_VERIFIED_APP_MANAGER_PID'
HOST_BUSYBOX='REPLACE_WITH_VERIFIED_HOST_BUSYBOX_PATH'
"$HOST_BUSYBOX" nsenter -t "$APP_PID" -m -u -i -n -p \
    -r"/proc/$APP_PID/root" -w"/proc/$APP_PID/root" -- /bin/sh
```

样本的管理进程名为 `appmgr`，不是所有固件的固定约定。没有核实进程、`nsenter` 支持和应用根目录就停止。不要为此新建容器、改现有应用管理器，或修改只读固件。

应用内新增文件通过**正在运行的应用环境**写入；不要直接从主系统改它正在使用的叠加文件系统底层目录，否则运行视图和落盘内容可能不一致。

## 五、为什么要编译两份 SSH 程序

两台 CPU 架构不同，不能交换可执行文件。还要核对位数、字节序和当前 CPU 能力；“都是 Linux”不足以判断兼容。

这次从 [Dropbear 2026.94 上游源码](https://matt.ucc.asn.au/dropbear/releases/dropbear-2026.94.tar.bz2) 编译，用 [Zig 0.13.0](https://ziglang.org/download/0.13.0/) 交叉编译，生成不依赖光猫系统动态库的版本。

本次使用的上游源码压缩包 SHA256：

```text
e098034a843699200c8c977a991fff73159735bf795d5f72ef672c41a6b1ae81
```

应从可信上游核对下载来源和完整性。摘要比对不是独立签名验证，也不证明程序没有漏洞。本发行包不附带编译器、Dropbear 源码或可执行文件。

下面是 **Linux 构建机** 上的复现示意，不在光猫上运行。先自行审阅并准备上述源码、编译器、`make`、`file` 等依赖，使用新的构建目录，不覆盖已有成果：

```sh
set -eu
ZIG='/absolute/path/to/zig'
SOURCE="$PWD/dropbear-2026.94"
for target in aarch64-linux-musl mipsel-linux-musl; do
    mkdir "build-$target"
    (
        cd "build-$target"
        CC="$ZIG cc -target $target" CFLAGS='-Os' LDFLAGS='-static' \
            "$SOURCE/configure" --host="$target" \
            --disable-pam --disable-zlib --enable-static \
            --disable-lastlog --disable-utmp --disable-utmpx \
            --disable-wtmp --disable-wtmpx
        make -j4 PROGRAMS='dropbear dropbearkey' MULTI=1 STATIC=1
        "$ZIG" objcopy --strip-all dropbearmulti dropbearmulti-stripped
        file dropbearmulti-stripped
        sha256sum dropbearmulti-stripped
    )
done
```

`dropbearmulti` 把服务端和主机密钥生成器放在一个文件内。要核对产物架构和静态链接，并在传输前、设备上分别比对摘要，不拿网上任意第三方二进制替代。二进制再分发还要保留上游组件的许可证，见 [第三方说明](../THIRD_PARTY_NOTICES.md)。

## 六、应用内安装哪些文件

安装前先确认这些位置是否已有用户文件。**已有服务、密钥或 `authorized_keys` 时先停下核对，不整份覆盖，也不默认批准旧授权列表访问新服务。**

| 应用内路径 | 用途和权限 |
|---|---|
| `/opt/ontssh/` | 新服务的专用目录，700 |
| `/opt/ontssh/dropbearmulti` | 对应 CPU 的程序，700 |
| `/opt/ontssh/hostkey` | 在这台光猫上新生成的 Ed25519 主机私钥，600 |
| `/root/.ssh/authorized_keys` | 只含已批准的客户端公钥，600，父目录 700 |
| `/etc/init.d/ontssh` | 审阅并修改后的启动模板，700 |
| `/etc/rc.d/S96ontssh`、`K05ontssh` | 样本原生启停链接，由已核实的 `rc.common` 机制创建 |
| `/var/run/ontssh.pid` | 本服务运行时的进程编号，不是持久化证据 |

应用的可写层保存在样本闪存 `/opt/upt/apps/apps/` 下，但这个路径不能推导成所有固件的统一布局。不要为找可写目录而改分区、刷机、启用未知启动分支或格式化数据。

安装材料只传程序、模板和**客户端公钥**。客户端私钥始终留在管理端安全存储，不能复制到光猫、文档或 Git。样本临时使用了限定来源的本地 TFTP，传输后核对摘要并删除临时规则；它没有加密和认证，不是通用推荐，更不能搬到公网。

主机私钥应在设备本地、确认目标文件不存在时生成，不能两台共用。客户端公钥行应带限制选项，示意如下，不是可用密钥：

```text
no-agent-forwarding,no-port-forwarding,no-X11-forwarding REPLACE_WITH_AUTHORIZED_PUBLIC_KEY
```

### 启动模板怎样使用

源码在 [tools/ont-ssh.init](../tools/ont-ssh.init)。这是 **OpenWrt 风格 `rc.common` 的 SAF 应用模板**，不是通用 Linux 服务安装器，不适用于 systemd，也不是让你覆盖主系统的 init。

1. 先阅读完整模板，在本地副本把 `LISTEN_ADDRESS` 占位符替换为现场确认的管理 IPv4。
2. 在已确认的应用环境准备程序、主机密钥、公钥及权限，保留原有用户文件。
3. 确认目标不存在后才安装为应用内 `/etc/init.d/ontssh`，先 `sh -n` 检查，再按当前 `rc.common` 实现启用和启动。
4. 独立检查创建的链接、服务参数、监听地址，并进行经过授权的密钥登录验证。

模板默认占位地址不能启动，只接受不带前导零的私有 IPv4，不回退到 `0.0.0.0`、主机名或 IPv6 全地址。**格式合法不代表地址正确**，仍须现场核对目标和可达范围。

它沿用样本的运行限制：

```text
dropbear -p <已核实的管理IPv4>:22 -r /opt/ontssh/hostkey
         -P /var/run/ontssh.pid -s -g -j -k -I 600 -K 30
```

- `-s` / `-g` 禁用密码和 root 密码登录，没有启用允许空密码的 `-B`。
- `-j` / `-k` 禁用 TCP 端口转发，公钥选项另行限制代理和 X11 转发。
- `-I 600` 是 600 秒空闲断开，`-K 30` 是每 30 秒保活，不是重启光猫。
- 地址尚未就绪时只有限重试自己的服务，不重启应用管理器，不改其他服务。
- `stop` 会核对 PID 对应的可执行文件，不用全局 `killall` 停 SSH。

原生启动项只登记了**应用启动时怎么启动 SSH**。当前能启动、链接存在和文件已落盘，都不能替代真正的重启验证；没有单独授权，不重启光猫来凑验收。

## 七、怎样避免两个站点的管理地址冲突

**下面所有地址和接口标记都是重新编写的示意，不是案例真实网络规划，不能直接导入。** 假设两台光猫管理地址均为 `192.168.1.1`，各自后级路由器的管理侧地址已现场确认是 `192.168.1.2`：

| 站点 | 管理端连接入口 | 路由器转送目标 | 光猫看到的连接来源 |
|---|---|---|---|
| 示例 A | 路由器内网 `192.168.10.1:2222` | 该站点光猫 `192.168.1.1:22` | 该站点 `192.168.1.2` |
| 示例 B | 路由器内网 `192.168.20.1:2222` | 该站点光猫 `192.168.1.1:22` | 该站点 `192.168.1.2` |

路由器这里只做地址转换，不是在路由器上另开 SSH：

- **去程 DNAT**：把“本路由器内网地址的 2222 端口”转给本站点光猫的 22 端口。
- **回程 SNAT**：把这条连接的来源换成光猫同管理网段内可回复的地址，否则可能有去无回。
- 两条都限制已确认的内网入口、管理出口、TCP 和目标端口，必要时再限制授权管理来源。
- 不使用公网拨号接口、全部接口或通配地址；不为省事新建、克隆网络连接配置。

iKuai 样本的普通 `network dnat` 接口拒绝内网入口参数，而高级 NAT 表能够表达这组规则。**命令预览成功不代表后端接受参数，更不代表已经能登录。** 遇到拒绝时不能改成公网或“全部接口”来硬凑。

本章不提供会直接改路由器的命令。应读取当前 CLI/API、接口与现有规则，先预览目标和保留项，经授权后写入并回读；规则 ID、接口名和源地址都不能照搬。IPv6 和已有公网映射要另行检查，仅绑定私有 IPv4 不是完整的可达性保证。

## 八、首次连接必须核对设备身份

从已经信任的临时控制台读取**主机公钥和指纹**，在管理端本地核对，再加入专用 `known_hosts`。不要打印或复制 `/opt/ontssh/hostkey` 私钥；本文不公开案例的真实公钥和指纹。

非默认端口记录格式如下，仍是占位示意：

```text
[192.168.10.1]:2222 ssh-ed25519 REPLACE_WITH_VERIFIED_HOST_PUBLIC_KEY_BASE64
```

不能靠“关闭主机校验”解决首次登录。端口转发到另一台设备时，主机身份变化必须能被发现。

这次还遇到 Windows OpenSSH 9.5 的 `ssh-keyscan` 选择已公布但不能完成的算法，报错：

```text
choose_kex: unsupported KEX method sntrup761x25519-sha512@openssh.com
```

这是这次客户端和服务端组合的兼容问题，不能仅凭它判定转发不通。我们从可信控制台取得主机公钥，正式客户端限定 `KexAlgorithms=curve25519-sha256`，保留严格主机校验，随后实际认证成功。不需要降级成弱口令或开放密码登录。

下面是 OpenSSH 连接形状，地址、客户端私钥位置和已核对的主机记录文件都必须替换为你自己的；私钥加密时需先通过你认可的安全方式解锁，不能把口令写进命令：

```sh
ssh -p 2222 -i "$HOME/.ssh/ont-maintenance" \
    -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes \
    -o UserKnownHostsFile="$HOME/.ssh/ont-known-hosts" \
    -o KexAlgorithms=curve25519-sha256 \
    root@192.168.10.1 'id; uname -m; readlink /proc/1/exe'
```

用于 Agent 时，把已核对的站点入口、主机身份和密钥引用加入你已有的连接管理器即可，不复制本案例的私有注册表或密钥。

## 九、验收什么，还剩什么

历史样本完成了实际密钥登录和命令执行，并回读：

- UID 为 0，架构与目标一致，应用 PID 1 为 `/sbin/procd`；
- Dropbear 版本、仅管理地址监听、禁密码和禁转发参数；
- `S96ontssh` 链接，以及 `.ssh` 700、授权公钥和主机私钥 600；
- 临时传输规则已移除，原有转发保留，没有新增公网 SSH/Telnet 映射；
- 两台临时 Telnet 监听均已关闭，而 SSH 仍然可用。

应用自带 BusyBox 可能比主系统的更旧，例如没有 `stat`，应使用已确认存在的 `ls -l` 等工具。远程命令不存在不是 SSH 登录失败。

关闭自己临时开启的 Telnet 服务后，要等服务端确实结束连接，再关闭客户端，并独立核对状态。过早断开客户端可能使清理没有执行完；不要顺手关闭别人原有的维护入口。

**还没有验证光猫整机或应用环境重启后的恢复。** 主系统命令链接恢复、真实厂商日志转发及其重启恢复，仍是独立工作，不能由“SSH 成功”推导为完成。固件升级、恢复出厂也可能清除应用数据，本教程不为验证这些场景而执行它们。

## 十、发布时怎样脱敏

只保留省份、型号、固件、CPU 架构、通用文件路径、程序版本、公开源码摘要和协议字段。移除真实站点、管理入口、接口编号、主机名、密钥与指纹、凭据、私人域名、原始日志和个人文件路径。

公开的是方法、经过改写的启动模板和明确的验证范围，不是生产配置导出、一键固化器或全型号安装器。Agent 的独立分支见 [SSH 参考](../skills/telecom-ont-maintenance/references/native-app-ssh.md)，隐私清单见 [09：脱敏](09-privacy.md)。
